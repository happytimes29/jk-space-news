# JK Space 個人工程實驗室 PRD

- 文件版本：1.0
- 日期：2026-10-14
- 狀態：提案，待站主確認
- 產品名稱：JK Space
- 產品定位：個人工程實驗室

## 1. 產品摘要

JK Space 將由自動彙整科技新聞的網站，轉型為一個以站主本人為核心的個人工程網站。網站不再追求新聞數量、更新頻率或媒體流量，而是集中呈現三種真正具有長期價值的內容：

1. 實際做過的工程專案與解題過程。
2. 能直接使用的工程工具與小型產品。
3. 站主親自撰寫的技術筆記、專案紀錄與新聞觀點。

首頁必須讓第一次造訪的人在 10 秒內理解：站主是誰、擅長什麼、做過哪些東西，以及下一步可以看什麼或使用什麼。

核心標語建議為：

> 把工程上的麻煩事，做成好用的工具。

## 2. 背景與問題

現有網站以「JK Space News」為品牌，首頁、導覽、搜尋、SEO 與內容架構均以自動化新聞為中心。這產生幾個問題：

- 網站無法清楚表達站主本人、專業能力與作品。
- 大量新聞內容的差異化有限，也容易稀釋真正重要的專案與工具。
- 自動新聞需要持續維護資料來源、排程與發布流程，卻未必能累積個人品牌資產。
- 訪客看完文章後，缺少進一步認識站主、試用工具或提出合作的路徑。
- 目前「工具」內容偏向工具推薦文章，尚未完整呈現可操作產品的價值。

本次改版要讓網站從「內容聚合站」變成「作品、能力與觀點的可信入口」。

## 3. 產品目標

### 3.1 主要目標

- 建立清楚一致的個人品牌「JK Space」。
- 用專案案例證明硬體研發、AI 自動化與獨立產品開發能力。
- 讓訪客能快速找到並使用站主開發的工具。
- 建立可長期累積的筆記與觀點系統。
- 保留對特定新聞發表個人看法的能力，但不恢復新聞聚合模式。
- 提供清楚、可信且無假資料的聯絡與合作入口。

### 3.2 非目標

V1 不包含以下功能：

- 自動抓取、摘要或批次發布新聞。
- 會員、登入、留言、論壇或社群系統。
- 付費訂閱、電子報寄送或金流。
- 後台 CMS、資料庫或複雜權限系統。
- 完整中英雙語站。
- 為追求發文頻率而產生大量 AI 內容。

## 4. 目標使用者

### 4.1 潛在合作夥伴或客戶

希望快速判斷站主是否具備硬體研發、PCB、測試流程、自動化或內部工具開發能力。

主要需求：

- 看懂站主的專長與經驗。
- 查看具體案例、角色、做法與成果。
- 找到聯絡或合作方式。

### 4.2 工程師與技術同好

因搜尋、社群分享或工具連結進站，想直接解決問題或了解技術細節。

主要需求：

- 快速使用工具。
- 查看輸入、輸出、限制與資料隱私說明。
- 閱讀可重現、有脈絡的工程筆記。

### 4.3 認識站主的人與一般訪客

想知道 JK Space 是什麼、站主最近在做什麼，以及有哪些值得追蹤的作品。

主要需求：

- 一眼理解網站定位。
- 看到精選作品與近期更新。
- 找到外部個人檔案或聯絡方式。

## 5. 品牌與內容原則

### 5.1 品牌名稱

- 對外名稱統一為「JK Space」。
- 不再使用「JK Space News」作為網站主品牌。
- 「News」不出現在網站標題、Logo、頁尾、主要導覽與預設 SEO 描述中。

### 5.2 品牌語氣

- 專業但不官腔。
- 以實際問題、限制、選擇與結果說話。
- 可以有個人觀點，但要區分事實、推論與立場。
- 不使用誇大成果、虛構數字、假見證或假合作案例。
- 技術內容優先說明「為什麼」與「怎麼驗證」。

### 5.3 內容品質門檻

每篇公開內容至少要回答其中一項：

- 這解決了什麼問題？
- 我做了什麼判斷？
- 實際結果或限制是什麼？
- 讀者可以如何使用或重現？
- 這則新聞為什麼值得我評論？

## 6. 資訊架構

主要導覽固定為：

1. 首頁 `/`
2. 專案 `/projects`
3. 工具 `/tools`
4. 筆記與觀點 `/notes`
5. 關於我 `/about`
6. 聯絡 `/contact`

行動版可收進選單，但順序保持一致。

### 6.1 舊路由處理

| 舊路由 | 新行為 |
| --- | --- |
| `/news` | 永久轉址至 `/notes` |
| `/news/[slug]` | 已移除內容回傳 404，並標示不建立索引 |
| `/trending` | 永久轉址至 `/notes` |
| `/profile` | 永久轉址至 `/about` |
| `/interviews` | 若無正式內容，V1 不出現在導覽；既有路由轉址至 `/notes` |
| `/feed.xml` | 保留網址，但內容改為「筆記與觀點」RSS |

## 7. 頁面需求

### 7.1 首頁

首頁是個人品牌與作品入口，不是文章列表。

由上至下包含：

#### A. Hero

- 顯示品牌名稱「JK Space」。
- 顯示一句明確定位，例如「硬體研發 × AI 自動化 × 獨立產品實驗」。
- 顯示核心標語「把工程上的麻煩事，做成好用的工具。」
- 主要 CTA：「查看專案」。
- 次要 CTA：「使用工具」。
- 不使用新聞輪播或今日熱門新聞。

#### B. 專業焦點

以三張卡片呈現：

- 硬體與高頻研發。
- AI 與工作流程自動化。
- 工程工具與獨立產品。

每張卡片包含一段不超過 60 字的說明，並連至相關專案或內容。

#### C. 精選工具

- V1 主推 PCB Test Point Comparison Tool。
- 顯示用途、適合對象、資料是否離開瀏覽器，以及「立即使用」按鈕。
- 若工具只有一個，使用單一大型區塊，不用製造空洞的工具目錄感。

#### D. 精選專案

- 顯示 2 至 4 個由站主指定的專案。
- 每張卡片顯示：專案名稱、問題摘要、站主角色、狀態與一項成果。
- 不以日期排序取代人工精選。

#### E. 最新筆記與觀點

- 顯示最近 3 篇站主原創內容。
- 新聞評論必須標示為「新聞觀點」，不得偽裝成原始新聞報導。
- 無內容時顯示簡潔空狀態，不放示範假文章。

#### F. Now／最近在做什麼

- 顯示一段可定期手動更新的近況。
- 包含更新日期。
- 可連向進行中的專案。

#### G. 合作 CTA

- 簡述可交流或合作的題目。
- 連至 `/contact`。
- 僅顯示已設定且真實有效的聯絡管道。

### 7.2 專案列表 `/projects`

- 頁首說明專案不只展示成品，也記錄問題、選擇與結果。
- 支援依領域篩選：硬體、AI 自動化、工具產品。
- 支援依狀態辨識：進行中、已完成、維護中、已封存。
- 精選項目優先，其餘依年份或更新日期排列。
- 卡片包含：名稱、摘要、角色、狀態、技術標籤、成果摘要。

### 7.3 專案詳情 `/projects/[slug]`

每個案例頁使用一致結構：

1. 專案摘要。
2. 問題與使用情境。
3. 站主的角色與責任範圍。
4. 限制與設計考量。
5. 解法與關鍵決策。
6. 實作過程或架構。
7. 結果、驗證方式與已知限制。
8. 圖片、流程圖或操作截圖。
9. 相關工具、程式碼或文章連結。
10. 最後更新日期。

若成果因保密無法公開，需明確說明可揭露範圍，不以模糊行銷詞取代證據。

### 7.4 工具列表 `/tools`

- 將頁面定位從「工具推薦」改為「我做的工具」。
- 每個工具顯示狀態：可使用、實驗中、維護中或已封存。
- 顯示主要用途、輸入格式、輸出結果與隱私特性。
- 可直接使用的工具必須有清楚的「開啟工具」按鈕。
- 介紹性文章與工具本體要能互相連結，但不混為同一件事。

### 7.5 工具詳情與應用頁

工具詳情頁包含：

- 問題與適用情境。
- 使用方式。
- 支援格式與限制。
- 資料處理與隱私說明。
- 範例輸入與預期輸出。
- 版本或最後更新日期。
- 已知問題與回饋入口。

互動工具頁需符合：

- 核心操作不要求登入。
- 若資料僅在瀏覽器處理，頁面要清楚標示。
- 錯誤訊息要能告訴使用者如何修正輸入。
- 提供範例檔或示範資料，讓訪客不需自行準備資料也能理解工具。

### 7.6 筆記與觀點 `/notes`

此區取代原本新聞中心，內容只收錄站主願意署名的原創文章。

固定分類：

- 工程筆記。
- AI 與自動化。
- 專案紀錄。
- 新聞觀點。

列表功能：

- 依分類篩選。
- 顯示標題、摘要、發布日期、分類、閱讀時間與標籤。
- 預設按發布日期新到舊排列。
- 不顯示自動生成的熱門排行。

### 7.7 筆記詳情 `/notes/[slug]`

一般文章包含標題、摘要、日期、分類、閱讀時間、正文與相關內容。

「新聞觀點」額外包含：

- 原始來源名稱。
- 原文連結。
- 事件或文章發布日期。
- 「事件摘要」與「我的觀點」兩個明確分區。
- 若引用數據或說法，正文內標明來源。
- 不能完整搬運原文，也不能只做無新增價值的摘要。

### 7.8 關於我 `/about`

- 延續現有「Hardware R&D × AI Automation」主軸。
- 呈現 15+ 年經驗時，避免只有年資數字，需搭配領域與代表成果。
- 包含簡介、專業領域、工作方法、經歷時間線、目前關注方向與外部連結。
- 個人照片不是 V1 必要條件；若沒有合適照片，可用字體、圖形與專案畫面建立辨識度。

### 7.9 聯絡 `/contact`

- 說明適合聯絡的主題，例如技術交流、工具回饋與合作討論。
- 只顯示在集中設定檔中已填入的真實聯絡方式。
- 未設定的 Email、Telegram、GitHub 或社群連結完全不渲染。
- V1 使用外部連結或 `mailto:`，不建立聯絡表單與後端寄信服務。

## 8. 內容模型

內容繼續使用 Markdown 或 MDX，保留 Git 版本管理，不引入 CMS。

### 8.1 Project

必要欄位：

- `title`
- `slug`
- `summary`
- `year`
- `status`: `active`、`completed`、`maintained`、`archived`
- `areas`: `hardware`、`automation`、`product`
- `role`
- `tags`
- `featured`
- `updatedAt`

選填欄位：

- `coverImage`
- `gallery`
- `demoUrl`
- `repositoryUrl`
- `relatedTools`
- `relatedNotes`
- `outcome`

### 8.2 Tool

必要欄位：

- `title`
- `slug`
- `summary`
- `status`: `available`、`experimental`、`maintenance`、`archived`
- `privacy`
- `inputTypes`
- `outputTypes`
- `updatedAt`

選填欄位：

- `appUrl`
- `coverImage`
- `sampleUrl`
- `repositoryUrl`
- `relatedProject`

### 8.3 Note

必要欄位：

- `title`
- `slug`
- `summary`
- `publishedAt`
- `updatedAt`
- `type`: `engineering`、`automation`、`project-log`、`commentary`
- `tags`
- `author`
- `featured`

新聞觀點額外必要欄位：

- `sourceTitle`
- `sourceUrl`
- `sourcePublishedAt`

選填欄位：

- `coverImage`
- `relatedProjects`
- `relatedTools`

### 8.4 SiteConfig

品牌與聯絡資料集中在單一設定來源，至少包含：

- 網站名稱。
- 標語。
- 預設 SEO 描述。
- 作者名稱。
- 可用的聯絡連結。
- GitHub 或其他公開個人檔案。

所有頁面共用此設定，避免 Logo、頁尾與 Metadata 出現不同名稱。

## 9. 舊新聞與資料保存策略

### 9.1 公開網站

- 移除首頁、導覽、搜尋、網站地圖與 RSS 中的舊新聞入口。
- 移除新聞輪播、最新新聞、熱門新聞與新聞專用 UI。
- 舊新聞詳情不繼續公開，不轉成站主觀點文章。
- 只有站主日後主動挑選並重新撰寫的內容，才能以全新的 `/notes/[slug]` 發布。

### 9.2 保存與回復

- 舊新聞在從主分支移除前，必須確認已有可讀的本機封存與 Git 備份分支。
- 既有備份分支 `backup/pre-reconciliation-2026-10-14` 作為歷史快照，不改寫。
- 本機封存需保留標題、slug、日期、來源、摘要與原始內容，以便人工查找。
- 封存資料不參與正式網站建置或部署。

### 9.3 SEO

- `/news` 與 `/trending` 使用永久轉址，將仍有意圖的訪客帶往 `/notes`。
- 已移除的 `/news/[slug]` 回傳 404 且不建立索引，避免保留大量低價值頁面。
- 新 sitemap 僅列出正式頁面、專案、工具與筆記。
- RSS URL 可沿用，但標題與內容改為 JK Space 筆記與觀點。

## 10. 搜尋與導覽行為

- 保留快速搜尋介面，但索引對象改為專案、工具與筆記。
- 搜尋結果清楚標示內容類型。
- 無結果時提供前往專案、工具與筆記列表的入口。
- 搜尋不得索引本機新聞封存資料。
- 麵包屑用於專案、工具與筆記詳情頁。
- 網站內不存在無法返回列表或首頁的孤立頁面。

## 11. 視覺與互動方向

延續現有深色科技感，但從「新聞媒體」調整為「工程工作台」。

### 11.1 視覺原則

- 深色為預設主題，可保留明暗模式切換。
- 使用低彩度中性色搭配一個主要藍色或青色強調色。
- 使用細緻網格、座標、線框或工程圖語彙，但避免影響文字可讀性。
- 卡片用於建立層級，不讓所有內容都變成相同大小的卡片。
- 首頁優先展示工具畫面、專案截圖或實際輸出，不使用無關的新聞封面拼貼。
- 動畫只用於狀態變化與導覽回饋，尊重 `prefers-reduced-motion`。

### 11.2 響應式需求

- 手機寬度 320px 起可正常使用。
- 導覽、篩選器、程式碼區塊、表格與工具操作不可造成水平頁面溢出。
- 主要 CTA 在小螢幕上仍位於首屏可見範圍。

## 12. SEO 與分享

- 全站預設標題改為「JK Space — 個人工程實驗室」。
- 預設描述聚焦硬體研發、AI 自動化、工程工具與技術觀點。
- 各內容頁具有獨立 title、description、canonical 與 Open Graph 資訊。
- 首頁使用 `Person` 與 `WebSite` 結構化資料。
- 工具頁在資訊完整時使用 `SoftwareApplication` 結構化資料。
- 文章頁使用 `Article`；新聞觀點不宣告為原始新聞出版者。
- 社群分享圖採用一致模板，包含類型、標題與 JK Space 品牌。
- V1 以繁體中文為主，HTML 語系設定為 `zh-Hant-TW`；英文僅作必要的專業術語與短副標。

## 13. 技術與營運需求

- 延續 Next.js、TypeScript、Tailwind 與 Vercel 部署。
- 內容建置保持靜態優先，減少伺服器與 API 依賴。
- 不新增資料庫、登入服務或付費第三方 CMS。
- 互動工具若可在瀏覽器完成，就不得上傳使用者檔案到伺服器。
- 若未來工具需要 API，必須在介面與隱私說明中揭露資料流向。
- 建置期間不得依賴本機新聞封存資料。
- 移除 OpenClaw 新聞發布流程後，相關密鑰、排程與文件需另行盤點；PRD 本身不授權刪除任何外部資源。
- GitHub 與 Vercel 的正式發布仍遵循現有主分支部署流程。

## 14. 分析與隱私

- V1 不新增廣告、追蹤像素或跨站行為分析。
- 若現有 Vercel Analytics 已啟用，可保留匿名頁面瀏覽與效能資料。
- 不收集未完成產品目標所需的個人資料。
- 聯絡頁不自行儲存表單資料。
- 工具頁必須清楚揭露檔案是否離開裝置。

## 15. 可及性與品質

- 所有互動元件可使用鍵盤操作。
- 可見焦點狀態不能被移除。
- 文字與背景色彩對比至少符合 WCAG 2.1 AA。
- 圖片需有合適替代文字；純裝飾圖使用空替代文字。
- 標題層級保持連續，單頁只有一個主要 `h1`。
- 動態狀態與錯誤提示需對輔助技術可讀。
- 正式發布前，首頁及各類型代表頁的 Lighthouse Accessibility 與 SEO 分數目標為 90 以上。
- 不以 Lighthouse Performance 單一分數作為唯一標準，但首頁在正常生產建置下不得有明顯版面跳動或阻塞式大型媒體。

## 16. 核心使用流程

### 16.1 合作方評估能力

成功條件：訪客不需閱讀新聞，就能理解站主專長、角色與可聯絡方式。

## 20. 風險與對策

### 20.1 首頁內容不足

風險：移除新聞後，頁面顯得空洞。

對策：優先使用一個成熟工具、兩個真實專案、三個專業焦點與 Now 區塊建立首頁；不以假文章填空。

### 20.2 舊新聞流量中斷

風險：既有搜尋結果失效。

對策：列表與熱門頁永久轉址；文章頁正確下架並更新 sitemap，不把無關新聞批量導向首頁。

### 20.3 專案描述過度抽象

風險：網站看起來像履歷口號，無法證明能力。

對策：專案頁強制包含角色、限制、決策、結果與驗證方式；能展示的地方使用真實畫面或輸出。

### 20.4 內容維護再次變成負擔

風險：分類太多或發文要求過高，導致網站停止更新。

對策：保留四個穩定分類，以 Markdown／MDX 發布；首頁只顯示少量精選與近期內容，不承諾固定發文頻率。

### 20.5 聯絡資訊未準備完成

風險：頁面出現假信箱或無效連結。

對策：所有聯絡方式由集中設定控制，未設定項目完全隱藏；聯絡頁仍可先說明適合交流的主題。
