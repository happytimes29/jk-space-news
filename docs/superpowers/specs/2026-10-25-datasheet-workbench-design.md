# Datasheet 工程工作台第一版設計規格

## 目的

建立一個可公開使用、以證據為核心的 Datasheet 工程工作台，協助使用者快速讀懂公開元件 Datasheet，並評估兩個料號在指定工作條件下能否互相替代。

第一版只正式支援 MLCC 陶瓷電容與屏蔽型功率電感。電解、鉭質、薄膜、超級電容、RF 高 Q 電感、共模電感、電晶體與電源 IC 保留為後續擴充，避免在資料模型、比較規則及測試資料尚未穩定前，把不同物理特性與判定邏輯混入同一套結果。

本專案同時是網站上的可操作工具與完整工程案例：Tools 提供實際操作，Projects 說明問題、架構、限制、驗證資料與可靠性設計。

## 使用者與核心價值

主要使用者是需要閱讀元件規格、選料或尋找替代料的硬體、電源與 RF 工程師。

工具不以「AI 幫你決定」為賣點，而是把分散在不同頁面、表格與測試條件下的規格整理成可核對的資料，再由固定規則執行單位換算與條件比較。使用者應能看見每一個結論的來源，並知道哪些是原廠明示、哪些是程式判定、哪些仍需人工確認。

## 第一版範圍

### 工作區一：快速讀懂 Datasheet

使用者上傳一份公開 PDF，選擇或確認元件類型後，系統輸出：

- 製造商、料號、文件版本與日期。
- 元件用途與規格摘要。
- 電容或電感的結構化關鍵參數。
- Absolute Maximum、Recommended／Operating Conditions 與 Typical Characteristics 的明確區分。
- 容易忽略的限制、降額條件與測試條件。
- 附頁碼、章節、表格名稱與原文的工程問答。
- 可勾選的設計檢查清單。

### 工作區二：替代料評估

使用者上傳原料與候選替代料兩份公開 PDF，確認元件類型並填寫實際工作條件。系統輸出：

- 並排規格比較矩陣。
- 單位正規化後的 min／typ／max 數值。
- 測試條件不同、資料缺失或不可直接比較的標記。
- 封裝、尺寸與關鍵額定值的阻擋項目。
- `可直接替代`、`條件式可替代`、`不建議替代` 或 `證據不足` 的結論。
- 每個比較項目的雙邊來源與原文。
- 可匯出的 Markdown／JSON 報告；PDF 匯出延後評估。

若使用者未提供工作條件，系統只能產生規格差異報告，不得給出替代料結論。

若 PDF 是包含多個容量、感量、封裝或額定值的 Family Datasheet，系統必須先列出辨識到的 Ordering Code，讓使用者選定原料與候選料的完整型號。完整型號尚未確認，或 Datasheet 無法把規格可靠地對應到該型號時，不得產生替代料結論。

### 替代結論契約

- `可直接替代`：使用者輸入的所有強制工作條件均通過；所有強制電氣欄位都有雙邊證據；封裝外形、尺寸、焊盤與端點配置相容；不需要修改 PCB、外部元件或製程。
- `條件式可替代`：所有硬性安全與額定條件通過，但存在使用者允許的容差差異、非強制性能差異，或需要 BOM／製程／應用條件確認的非 PCB 變更。結果必須列出成立條件。
- `不建議替代`：任何強制額定值、工作範圍、封裝／焊盤或使用者指定限制不通過。
- `證據不足`：任一強制欄位缺失、衝突、無法對應 Ordering Code、測試條件不可比，或判定所需資訊只存在於第一版無法量化的圖表中。

使用者在工作條件表單中將每項限制標為強制或偏好；沒有指定的安全性、額定值、封裝與溫度條件仍視為強制項目。

## 元件規格模型

### MLCC 陶瓷電容

第一版結構化欄位：

- 電容量、容差與可選值系列。
- 額定電壓與降額條件。
- 介質／材質、溫度係數與工作溫度。
- ESR、阻抗、Ripple Current、Dissipation Factor 與漏電流。
- DC Bias、頻率及溫度對容量的影響。
- 封裝尺寸、端接材質與安裝形式。
- 壽命或可靠性條件；Datasheet 未提供時明確標記缺失。

替代評估所需工作條件：目標容量、DC 電壓、Ripple 頻率與電流、環境溫度、容許尺寸及必要介質。

### 屏蔽型功率電感

第一版結構化欄位：

- 電感值、容差與測試頻率。
- 額定電流、RMS 電流、飽和電流及其判定基準。
- DCR、SRF、Q 值與測試條件。
- 磁芯／屏蔽形式與工作溫度。
- 溫升條件、降額曲線與感量隨電流變化。
- 封裝尺寸與安裝形式。

替代評估所需工作條件：目標電感值、RMS 電流、峰值電流、開關或工作頻率、環境溫度、最大 DCR 及容許尺寸。

## 資料與證據模型

所有 AI 抽取結果必須轉成共同資料結構：

```ts
interface SourceEvidence {
  documentId: string;
  page: number;
  section?: string;
  table?: string;
  quote: string;
  chunkHash: string;
}

interface SpecificationValue {
  field: string;
  rawValue: string;
  normalized?: {
    min?: number;
    typical?: number;
    max?: number;
    unit: string;
  };
  conditions: string[];
  evidence: SourceEvidence[];
  status: "extracted" | "missing" | "ambiguous" | "conflicting";
}
```

頁碼與原文由本地 PDF 解析結果產生，不使用模型自行回憶的引用。`chunkHash` 用來確認回答引用的是本次上傳文件中的實際文字片段。

## 確定性比較引擎

確定性程式是普通 TypeScript 邏輯；相同的結構化輸入必須得到相同結果。它負責：

- 將 pF、nF、µF、mΩ、Ω、kHz、MHz、mA、A 等單位轉成共同基準。
- 保留 min／typ／max 與測試條件，不把 typical 當成保證值。
- 區分工作範圍、最大額定值與特性曲線。
- 驗證使用者的工作條件是否落在候選料的保證範圍。
- 比較封裝尺寸、容差、溫度、額定值及類別專屬參數。
- 在條件不一致、欄位缺失或來源互相衝突時停止自動結論。
- 依版本化規則產生比較狀態與原因碼。

大模型不得直接覆寫確定性程式的結果。它只能解釋結果，或把無法抽取的欄位標記為需人工確認。

## PDF 處理與檢索

- PDF 在瀏覽器端解析，不把原始檔永久上傳到網站伺服器。
- 第一版只接受文字型 PDF；掃描影像、加密 PDF 與無法取得文字層的文件顯示明確錯誤。
- 解析結果保留文件、頁碼、段落與表格線索，並在瀏覽器記憶體中分段。
- 使用章節名稱、料號術語與關鍵字進行本地檢索；第一版不依賴向量資料庫或另一組 Embedding API。
- 送往模型的是相關文字片段與 JSON Schema，不是無限制地把整份 PDF 塞入單一 Prompt。
- 使用者在分析前看見頁數、預估文字量、預估 API 呼叫次數與將送出的資料說明。
- 第一版不從曲線圖、掃描表格或圖片量測數值。若 DC Bias、Ripple、溫度降額、感量隨電流變化或飽和特性只能從圖形取得，系統保留圖表所在頁面作為人工檢查入口，並將相關自動判定降級為證據不足。

第一版以本機上傳 PDF 為入口。從任意網址抓取 PDF 涉及 CORS、重新導向與 SSRF 風險，列為後續功能。

## AI 與 BYOK 架構

### 共同介面

```ts
interface LlmAdapter {
  testConnection(config: ProviderConfig): Promise<ModelCapabilities>;
  extractSpecifications(input: ExtractionInput): Promise<SpecificationSet>;
  answerWithEvidence(input: QuestionInput): Promise<CitedAnswer>;
}
```

第一版提供：

- OpenAI-compatible adapter：支援可設定的 Base URL、Model ID 與結構化輸出能力。
- Anthropic Messages adapter。
- Google Gemini Generate Content adapter。

Provider 設定包含供應商、API 位址、API Key、模型名稱與能力測試。系統先送出小型測試請求，確認連線與 JSON 結構輸出能力，再允許分析 PDF。

不支援 JSON Schema 的模型可使用嚴格 JSON Prompt 與一次修復重試；第二次仍無效即停止，不以猜測方式繼續。

### 暫時性 Relay

- API Key 預設只保存在當前頁面的記憶體，重新整理後消失。
- Key 經 TLS 傳送到 Relay，再轉交模型供應商；Relay 不寫資料庫、不寫 Log、不設定 Cookie、不快取 Request Body。
- 錯誤、遙測與分析事件必須先移除授權 Header、Key、PDF 內容及 Prompt。
- Relay 設定請求大小、回應大小、逾時、併發與速率限制。
- 自訂 OpenAI-compatible Base URL 只允許 HTTPS；阻擋 localhost、私有／保留 IP、非標準連接埠與未重新驗證的重新導向，以避免 SSRF。
- UI 必須在第一次傳送前明確說明：Key 會短暫經過 JK Space Relay，PDF 文字片段會送給使用者選擇的模型供應商。
- 使用者可隨時清除 Key、解析資料與分析結果。

## AI 工作方式

每次分析拆成可驗證步驟：

1. 本地解析 PDF 並建立頁面分段。
2. 本地規則定位可能相關的章節與表格。
3. Adapter 要求模型依指定 Schema 抽取欄位與引用的 chunk ID。
4. 程式檢查引用是否真的存在、數值是否能解析、單位是否受支援。
5. 無效欄位退回一次針對性修復；仍失敗則標記 ambiguous。
6. 確定性引擎執行正規化與比較。
7. 模型只根據比較結果與已驗證證據產生繁中、簡中或英文說明。

## 介面與流程

工具入口提供兩個醒目模式：`快速讀懂` 與 `替代料評估`。

共同流程：

1. 設定模型供應商並測試連線。
2. 上傳 PDF，檢查頁數、文字層與元件類型。
3. 顯示資料傳送說明與分析規模，使用者按下開始分析。
4. 逐步顯示解析、抽取、驗證及完成狀態。
5. 結果中的每一項規格均可展開來源頁碼與原文。

替代料模式另要求工作條件表單，結果頁依序顯示：總結、阻擋項目、條件式風險、比較矩陣、缺失資料與雙邊來源。

網站介面沿用繁中、簡中與英文路由。模型回答依目前語言輸出；原文引用保持 Datasheet 原始語言。

## 錯誤與降級行為

- PDF 無文字層：停止並說明第一版不支援 OCR。
- 無法辨識為電容或電感：允許使用者手動選擇；資料模型仍不匹配時停止。
- API 驗證失敗：不保存 Key，顯示去敏後的供應商錯誤。
- Rate limit 或逾時：保留本地解析進度，允許使用者重試尚未完成的步驟。
- 引用不存在：拒絕該欄位，不展示無來源數值。
- 同一欄位多個衝突值：全部展示並標記 conflicting，不自行選一個。
- Family Datasheet 無法把規格唯一對應到 Ordering Code：要求使用者重新選擇或標記證據不足。
- 必要參數只存在於曲線圖：顯示圖表頁碼並要求人工確認，不對圖形做數值內插。
- 任一強制替代條件缺失：最終結果只能是證據不足。

## 採用方案與取捨

### 方案 A：把整份 PDF 直接交給大模型

開發速度最快，但引用與數值難以驗證、供應商能力差異大、成本不透明，也容易把 Typical 或 Absolute Maximum 誤當成設計值，因此不採用。

### 方案 B：完全使用固定 Parser 與規則

數值比較可靠，但不同廠商的表格結構、用詞與跨頁限制差異很大，維護成本高，也難以提供自然語言問答，因此不採用。

### 方案 C：證據優先的混合架構（採用）

本地 Parser 建立可追溯文字，模型負責結構化與說明，確定性程式負責單位、範圍及替代判斷。成本較高、需要維護 Adapter 與測試資料，但最符合工程可靠性及多模型需求。

## 安全、隱私與成本

- 只處理使用者聲明為公開的 Datasheet；介面明確禁止上傳內部規格、電路圖或機密文件。
- 不建立帳號、文件庫、歷史分析資料庫或共用索引。
- 不保存 API Key、PDF 或 Prompt。
- 顯示實際 API 呼叫次數與供應商回傳的 Token Usage；不宣稱精確金額，因不同供應商與模型費率不同。
- 使用者必須主動按下分析才會產生 API 請求。
- Relay 需具備 CSRF／Origin 驗證、SSRF 防護、輸入大小限制與秘密資訊去敏測試。

## 非目標與反目標

第一版不包含：

- 電晶體、MOSFET、BJT、電源 IC 或其他元件的正式替代判定。
- OCR、掃描 PDF、網頁搜尋、Datasheet 自動下載與供應鏈價格。
- 自動電路設計、原理圖分析、BOM 管理與採購建議。
- 沒有工作條件仍輸出肯定替代結論。
- 以 AI 信心分數取代證據與規則。
- 將 API Key 存到 Local Storage、Cookie、資料庫或分析服務。

即使介面操作成功，只要結論沒有可核對來源、把 Typical 當保證值、忽略測試條件或暗示工具能取代工程審查，都視為產品失敗。

## 執行階段

### 階段 1：資料契約與驗證基準

- 定義電容、電感、證據、工作條件與比較結果 Schema。
- 選取多家廠商的公開 Datasheet 作為測試語料，建立人工核對的黃金資料。
- 建立單位轉換、範圍及原因碼測試。

### 階段 2：PDF 與證據管線

- 完成本地 PDF 解析、頁面分段、章節定位與文字型 PDF 檢查。
- 建立引用檢查、chunkHash 與來源展開 UI。
- 不接模型先完成可重現的解析測試。

### 階段 3：BYOK Relay 與多模型 Adapter

- 完成 Key 記憶體生命週期、連線測試及能力探測。
- 實作 OpenAI-compatible、Anthropic 與 Gemini adapter。
- 完成 Relay 去敏、限制、SSRF 與供應商錯誤測試。

### 階段 4：快速讀懂 Datasheet

- 建立抽取、驗證、摘要、問答與設計檢查清單。
- 完成三語介面、引用來源與 API 使用量呈現。

### 階段 5：替代料評估

- 建立電容與電感的工作條件表單。
- 完成雙文件比較矩陣、阻擋項目、原因碼與最終結論。
- 支援 Markdown／JSON 報告匯出。

### 階段 6：網站整合與工程驗證

- 建立 Tool 頁、App 頁及 Project 案例頁。
- 執行桌面／手機、鍵盤、三語與 reduced-motion 驗證。
- 使用黃金資料評估欄位抽取率、引用正確率、單位比較與最終判定。

## 成功標準

- 支援文字型公開 MLCC 與屏蔽型功率電感 Datasheet。
- Family Datasheet 必須先選定完整 Ordering Code，且所有比較值均能追溯到該型號。
- 每個展示的規格值都有可開啟的實際頁碼與原文。
- 確定性單位與範圍測試全部通過。
- 黃金資料中的強制阻擋條件不得被判成可替代。
- `可直接替代` 必須同時通過強制工作條件與封裝／焊盤相容性，不需要 PCB 修改。
- 缺失、衝突與不同測試條件能正確降級為人工確認或證據不足。
- API Key、PDF 內容與 Prompt 不出現在資料庫、Cookie、一般 Log 或分析事件中。
- OpenAI-compatible、Anthropic 與 Gemini 至少各用一個模型通過相同抽取契約測試。
- 手機與桌面均能完成上傳、分析、引用查看、比較與匯出流程。
- Projects 頁能清楚呈現問題、架構、驗證方法與限制，而不只是工具連結。

## 後續擴充

規格模型與比較引擎穩定後，再依序加入 MOSFET／BJT 與電源 IC。新增元件類型必須同時提供專屬 Schema、工作條件、比較規則、黃金資料與錯誤降級行為；不得只增加 AI Prompt。
