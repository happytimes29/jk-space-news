## 📰 1. 三支被忽略的AI能源股票，現在就買

🔗 [原文連結](https://finance.yahoo.com/energy/articles/3-under-radar-ai-energy-165000337.html)

## 原文摘要

這篇來自Yahoo Finance的文章點名了三支「雷達下」的AI能源股票，認為現在是進場時機。但說真的，原始內文塞滿了JavaScript和追蹤程式碼，實際投資分析幾乎被埋沒在技術堆裡。從標題和上下文推測，作者應該是在推薦那些同時吃AI運算與能源轉型紅利、但尚未被市場瘋狂追捧的公司——可能是數據中心電力供應商、智慧電網業者，或是用AI優化能源探勘的企業。

## 我的觀點：這種「低調股」不能只看概念，要看落地能力

直接說核心判斷：**AI能源股確實有成長空間，但「被忽略」往往不是因為市場笨蛋，而是因為商業模式還沒被驗證。** 我贊成關注這條賽道，因為AI對電力的需求正在爆炸——單一GPT-4訓練就吃掉幾千戶家庭一年的用電量。但「under-the-radar」的股票往往流動性差、波動大，而且很多只是掛著AI招牌的傳統能源公司。如果你只看新聞標題就衝進去，可能變成接盤俠。應該先查這三家公司有沒有實際的AI專案（比如用機器學習優化電網調度），還是只會發公關稿。

## 延伸思考：AI會不會讓能源問題更惡化，還是反而成為解方？

這其實是更大的問題。AI需要大量算力，算力需要大量電，而目前多數電力仍來自化石燃料。如果我們用AI來「更有效率」地挖石油，那只是延緩轉型。真正有價值的股票，應該是那些幫數據中心降低PUE（電力使用效率）、開發核融合控制系統、或是用AI預測再生能源出力的公司。另外，散戶投資者要避開「概念股」陷阱——很多小公司只要在新聞稿裡加入「AI」和「ESG」兩個詞，股價就能噴一波。建議用「營收佔比」來篩選：AI或能源相關業務有沒有貢獻實際收入？如果沒有，那就是題材股，不是價值股。

> 📝 編輯說：:這篇文章在Yahoo Finance引發討論，但原始碼混亂，筆者反而覺得最有價值的觀點是「別被低調兩個字迷惑，先看公司財報有沒有AI營收」。投資前多做功課，比看新聞標題重要一百倍。

## 📰 2. SpaceX股價從IPO後高點回落，現在該買進嗎？

🔗 [原文連結](https://finance.yahoo.com/markets/stocks/articles/spacex-stock-buy-falling-post-170500103.html)

## 原文摘要

這篇來自Yahoo Finance的報導討論了一個有點尷尬的問題：SpaceX股票能不能買？等等，SpaceX不是還沒IPO嗎？沒錯，但它在二級市場早就有人在交易了——員工持股、私募基金轉讓，讓這家公司有了一個「類IPO」的價格。報導指出，SpaceX的估值一度衝上約1500億美元，但最近幾個月已經跌回1200億左右，從那個所謂的「後IPO高點」摔了20%。分析師的意見兩極：多頭覺得星鏈（Starlink）的用戶數持續成長，星艦（Starship）也快要商業化，跌下來正是上車機會；空頭則認為這個估值還是太扯，而且馬斯克天天搞推特（現在叫X）分心，公司沒有上市就沒有散戶能直接買，流動性差到爆。

## 我的觀點

從報導中的關鍵數字來看，1200億美元估值對應的2024年預估營收約150億美元，本益比? 別傻了，SpaceX現在還在燒錢，星鏈要盈利還要好幾年。我的判斷是：這根本不算什麼「買點」，比較像是市場在給過熱的太空夢潑冷水。SpaceX的確是業界翹楚——發射成本比競爭對手低一大截，星鏈的覆蓋規模無人能及——但問題是，這種二級市場交易的水很深。你以為你在「買低」，結果可能只是接了一張沒有流動性的股票，甚至連投票權都沒有。普通投資人與其煩惱這個，不如等真正IPO那天再研究。而且說真的，馬斯克的注意力那麼分散，SpaceX會不會被當成提款機來補特斯拉或X的洞？這才是真正該擔心的風險。

## 延伸思考

這件事其實反映了更大的趨勢：科技獨角獸的估值在縮水。2021年那種錢多到沒處花的盛世已經過去了，現在投資人更看重現金流和可持續成長。SpaceX雖然是特例——它有國家安全訂單、衛星網路獨佔優勢——但連它都跌，其他太空新創（比如Rocket Lab、Astra）早就腰斬再腰斬。對於想押注太空產業的人，與其追一家沒上市的公司，不如看看相關的供應鏈廠商，比如做衛星零組件的、做地面接收站的，至少這些有財報可以看。另外，星鏈的「殺手級應用」——給偏遠地區提供網路——到底能不能撐住用戶成長和ARPU？如果沒那麼樂觀，那1200億的估值可能還是太貴。總之，別跟著媒體標題起舞，先搞懂你買的是什麼再出手。

> 📝 編輯說：: 這篇文章在科技投資人社群引發討論，筆者認為最有價值的觀點是：別把二級市場的價格當成真正的市場價格，流動性風險比你想像的大得多。

## 📰 3. Rob Pike – 'Concurrency Is Not Parallelism' [video]

🔗 [原文連結](https://vimeo.com/49718712)

TITLE: Rob Pike – '並行不是平行' [影片]

你有沒有遇過這種狀況：寫多執行緒程式時，以為開了幾個 thread 就是平行處理，結果效能反而卡成狗？甚至比單執行緒還慢？如果有，你很可能踩了 Rob Pike 在他那場經典演講《Concurrency Is Not Parallelism》裡反覆強調的坑。這支影片雖然被 Vimeo 的防機器人驗證擋住（超煩），但光是標題就值得我們挖出來好好聊一聊。

## 原文摘要：並行與平行，根本不是同一回事

Rob Pike（Go 語言的共同設計者）在這場演講裡講白了：**並行（concurrency）是一種「結構」設計，而平行（parallelism）是「執行」特性**。他舉了很多例子，最經典的是用一個「處理檔案」的工作流程來說明——你可以把任務拆成多個獨立的 goroutine 分別處理，但你的 CPU 可能只有一顆核心，那這些 goroutine 還是會輪流跑，不會真的同時執行。這就是**並行**：你在設計上讓多個任務可以「交錯進行」，但實際跑起來不一定平行。反過來說，如果你只是把一堆計算丟到多核心上，但它們之間完全沒有獨立性跟協調，那就只是平行而已，根本不是並行設計。

簡單來說：**並行關乎「怎麼拆」與「怎麼組合」；平行關乎「越快越好地跑」。**

## 我的觀點：工程師最常犯的兩個字陷阱

你知道嗎？很多人在面試或寫 Code 時，一口一個「平行處理」，其實心裡想的都是「同時做很多事」。但 Rob Pike 的觀點狠狠打臉這種懶人思考。為什麼這個區別很重要？因為如果你只是為了「快」而平行，卻沒想清楚每個任務的依賴關係，你很快就會撞上死鎖、資源競爭，甚至效能倒退。反過來，如果你先從**「並行結構」**下手——把問題拆成獨立、可組合的小單元，再用 goroutine、channel 或類似機制去協調，那就算你只有一顆核心，程式也能保持邏輯清晰，日後要真正平行擴充時，只需調整執行環境就好。

我個人最感觸的是，很多開發者（包括以前的我）都太急著追求「速度」，卻忽略了**「設計的正確性」**。就像 Rob Pike 說的：Concurrency 是關於 composition，不是關於 execution。你看 Go 語言把 goroutine 做得很輕量、讓並行設計變簡單，而不是直接給你 thread pool，就是這個道理。

## 延伸思考：從語言設計到日常專案的啟發

這場演講雖然是十多年前的，但放到現在依然超實用。尤其在多核 CPU 已經普及、雲端服務要應付大量請求的今天，錯誤的平行化策略只會讓系統更難維護。延伸想想：你在寫一個 REST API 時，如果只是用 async/await 把所有請求平行送出，卻沒考慮速率限制和 context 取消，那你的 server 大概很快就會爆炸。反過來，如果你是先定義好每個請求的「獨立單位」和「溝通方式」，再用 goroutine 或 event loop 來安排，程式碼的可讀性和可擴展性就會好很多。

另一個有趣的面向是團隊協作。很多專案之所以變成大泥球，就是因為不同工程師各自「平行」開發，卻沒有從整體架構上設計「並行」的模組邊界。結果程式碼之間互相依賴，像 spaghetti 一樣纏在一起。其實也可以套用同樣的思維：先把模組拆清楚，定義好訊息傳遞（API 合約），再讓團隊平行推進，這樣才不會亂。

## 結語

Rob Pike 這場演講雖然被驗證頁面擋住（有夠煩，讓我想到一些串流平台），但概念不減價值。如果你還沒看過，建議去 YouTube 找完整版（Vimeo 那個頁面可能只是偽裝），大概 30 分鐘，看完你對並行程式的理解會提升一個檔次。

> 📝 編輯說：: 這篇演講討論在 Hacker News 和 PTT 的 C_and_CPP 板都曾引發熱議，筆者認為最有價值的觀點是把「並行」從執行細節拉高到設計層次，值得每位寫多執行緒程式的人反覆思考。
