## 📰 1. Jensen Huang Scores Big in Japan -- Here's How to Follow the Nvidia CEO's Lead as the Country Transforms Into a $124 Billion AI Hub

🔗 [原文連結](https://finance.yahoo.com/technology/ai/articles/jensen-huang-scores-big-japan-090000711.html)

TITLE:黃仁勳在日本大獲全勝——跟著Nvidia CEO的腳步，見證日本蛻變為1240億美元AI樞紐

## 原文摘要

這篇報導的核心很簡單：Nvidia創辦人黃仁勳最近在日本動作頻頻，從出席半導體展會、拜會首相，到宣布與日本本土企業合資建立AI研發中心。日本政府更喊出要將AI相關產業規模推上1240億美元（約18兆日圓），目標是十年內讓日本從「失落三十年」的陰影中轉型成全球AI重鎮。文中特別強調，黃仁勳的策略不只是賣晶片，而是透過技術聯盟與在地化布局，讓Nvidia深度綁定日本供應鏈——這對投資人來說，是觀察半導體地緣政治與AI硬體需求的重要信號。

## 我的觀點：Nvidia的「日本攻略」其實是一盤很精明的長線棋

很多人以為黃仁勳最近衝日本只是去「收割訂單」，但我更傾向把它看成一次**防禦性擴張**。日本在晶圓製造（尤其是先進封裝與材料）仍有不可取代的優勢，像是信越化學、東京電子這些公司，Nvidia如果沒有把日本綁進自己的生態系，未來萬一供應鏈被掐住，輝達會非常痛苦。所以這不是單純的商業秀，而是一場供應鏈去風險的實戰操作。

此外，日本政府願意砸錢補貼AI與半導體，背後其實是對中國技術管制的間接回應。Nvidia剛好卡在中美科技戰的縫隙裡，日本成了它最安全的「備胎市場」。投資人如果只看短期的股價波動，很容易忽略這種「以日本為跳板，鞏固亞洲盟友」的長期戰術。

## 延伸思考：小散戶能學到什麼？

我們不是黃仁勳，沒辦法直接跟日本首相吃飯，但他的策略邏輯可以套用到個人投資：

1. **跟著供應鏈的「隱形冠軍」走**：不要只追Nvidia本身，日本那些做關鍵材料、設備、散熱技術的中小企業，未來五年很可能因為AI需求而市值翻倍。例如生產高頻寬記憶體（HBM）的廠商，或是做先進封裝檢測的公司。

2. **留意政策紅利的地域性**：日本政府補貼AI研發的條件之一，是要求企業必須在當地設廠並雇用本地工程師。這會帶動日本軟體人才培訓與數據中心建置，相關的房地產信託（REITs）或能源基礎建設也可能受惠。

3. **風險提醒**：日本文化中的「年功序列」與緩慢決策流程，可能會拖累AI新創的速度。Nvidia能快速落地，不代表其他外國企業也能複製。投資日本AI相關標的時，要留意管理層是否真的敢於改革。

## 📰 2. OpenAI reduces Codex Model Context Size from 372k to 272k

🔗 [原文連結](https://github.com/openai/codex/pull/33972/files)


TITLE: OpenAI縮減Codex模型上下文長度：從372K到272K的取捨

## 原文摘要

根據最新技術報導，OpenAI悄悄調整了旗下Codex模型的上下文視窗大小，從原本的372,000 tokens（約372K）一口氣砍到272,000 tokens（272K），縮水幅度接近27%。雖然官方沒有大張旗鼓宣布，但這項變動已經在開發者社群引發不少討論——畢竟Codex是專門用來生成程式碼的模型，上下文越長，理論上能處理更完整的專案結構和依賴關係。現在硬生生少掉100K，意味著模型能「記住」的程式碼片段、註解和歷史對話都變少了。背後原因推測是為了降低運算成本和推論延遲，讓模型在商業部署上更划算。

## 我的觀點

100K tokens可不是小數目，這個數字大約等於7.5萬個英文單詞，或者是一整本《老人與海》的篇幅。OpenAI砍掉這麼多上下文，表面上看是「縮水」，但仔細想想其實很合理：大部分開發者寫程式根本不會一次餵給模型30萬字以上的上下文，真正有用的往往是最新幾百行程式碼和當前檔案。從成本角度切入，維持超大上下文需要龐大的GPU記憶體和注意力計算，這對API定價和伺服器負載都是巨大壓力。我的判斷是：這不是「閹割」，而是務實的產品優化——與其讓95%的使用者為那5%的極端場景買單，不如先把資源集中在大多數人常用的範圍內。

不過風險也很明顯：如果你正在用Codex做大型重構、跨檔案分析，或是整合多個微服務的程式碼庫，突然縮小的上下文可能會讓模型「失憶」，導致生成的程式碼遺漏關鍵邏輯。OpenAI顯然在賭——賭多數人不會用到極限，或者他們會推出更高階的付費方案來提供完整版。

## 延伸思考

這件事其實反映了AI產業一個更深的矛盾：模型的「能力上限」與「實際可用性」之間的取捨。超大上下文就像一台卡車的載重上限——你可以宣稱能載10噸，但真正上路時油耗、路況、法規都會逼你只載5噸。OpenAI這次調整等於主動把載重上限調低，換取更穩定的營運和更低的API價格。

對開發者來說，這是個警訊：別再盲目追求「越大越好」的模型規格。與其抱怨上下文被砍，不如調整自己的工作流程——把專案切成更小的模組、善用RAG（檢索增強生成）補足歷史資訊、或是乾脆改用其他支援動態上下文的模型。另外，這件事也暗示了OpenAI可能在為下一代模型鋪路：更小的上下文但更強的推理能力，說不定才是未來的方向。

筆者認為這篇最有價值的觀點是：AI模型的效能優化不該只靠堆參數，而是要在真實使用場景中找到平衡點。這對整個產業的產品設計策略都有啟發。

## 📰 3. Claude Code uses Bun written in Rust now

🔗 [原文連結](https://simonwillison.net/2026/Jul/19/claude-code-in-bun-in-rust/)

TITLE:Claude Code 現在使用了以 Rust 重寫的 Bun

## 原文摘要：抓出藏在二進位檔裡的 Rust 痕跡

Simon Willison 不愧是細節控，他讀到 Jarred Sumner 說「Claude Code v2.1.181 之後改用 Rust 版本的 Bun」，好奇心立馬爆炸，直接對自己的 Claude Code 安裝目錄下手。他用 `strings` 指令翻了翻二進位檔，先找到 `Bun v1.4.0` 這個版本號——比 GitHub 上公開的 v1.3.14 還新，顯然是用了 preview 或 canary 版。接著又 grep 出一長串 `.rs` 檔名，從 `src/runtime/bake/dev_server/mod.rs` 到各種 bundler 相關檔案，總共 563 個。證據確鑿，Rust 重寫的 Bun 真的被塞進 Claude Code 裡，在全球數百萬台裝置上跑起來了。

Jarred 說得雲淡風輕：「啟動快了 10%，Linux 上更明顯，但幾乎沒人注意到。無聊就是好事。」Simon 也認同，這是件低調但紮實的工程成就。

## 我的觀點：當升級「無感」才是最強的使用者體驗

你每天用 Claude Code 寫程式時，會不會好奇背後到底是哪個 runtime 在撐？我猜大部分人都不知道，也不想知道——因為這本來就不是該你操心的事。Claude Code 團隊偷偷把 Bun 從原本的 Zig 實作換成 Rust 版本，效能提升 10%，但你完全不用改任何設定、不用看 migration guide、甚至不用重新下載。這種「換引擎」居然能做到跟換燈泡一樣安靜，才是真正的工程功力。

我自己很喜歡 Jarred 說的「Boring is good」。很多時候開發者把「升級」搞得太戲劇化，動不動就 breaking changes、新 API 大洗牌，搞得大家戰戰兢兢。但真正的生產力工具，應該是像空氣一樣——你感受不到它的存在，但它就是讓一切跑得更順。Claude Code 這次的操作，等於用 Rust 的效能優勢（記憶體安全、編譯優化）換取無痛體驗，既保留了原本 Bun 的相容性，又偷偷把底層升級了。這才是成熟專案該有的姿態。

## 延伸思考：Rust 重寫潮背後的工程哲學

這不是第一個用 Rust 重寫的知名專案，從 ripgrep、delta 到現在 Bun 的移植，Rust 正在默默吃掉各種基礎設施層。但有趣的是，Claude Code 是 LLM 輔助開發工具，使用者對它的 runtime 幾乎無感，團隊卻願意花力氣做這項移植——10% 的啟動加速在某些場景下可能很關鍵（比如 CI pipeline 或大量短暫的 CLI 呼叫），但對一般互動式使用來說，真的差別不大。那為什麼要做？

我猜動機有兩個：一是 Rust 的生態更成熟，對跨平台支援更好，長期維護成本較低；二是安全層級的提升，尤其 Claude Code 會處理敏感程式碼，Rust 的記憶體安全保證能降低潛在漏洞。這種「看不到的投資」往往比瘋狂加功能更值得尊敬。

不過話說回來，這也對使用者提出一個反思：我們是不是太習慣只看功能更新，而忽略了那些「無聊但重要」的基礎建設升級？下次你的工具突然變穩定了，說不定就是某個團隊在背後默默用 Rust 重寫了一次。
