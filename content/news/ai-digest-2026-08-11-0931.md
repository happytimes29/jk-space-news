## 📰 2. What's the best programming language for coding agents?

🔗 [原文連結](http://danluu.com/pl-tokens/)

TITLE: 對 AI 編碼代理來說，哪種程式語言最好？

## 原文摘要

最近有一篇在 Patreon 上被到處轉貼的文章，標題就是「What's the best programming language for coding agents?」，作者拿了不少程式語言來比較，發現動態語言或寫起來比較精簡的語言，在餵給 LLM 時 token 消耗明顯比較少。他甚至舉例說 C 和 Clojure 之間有 2.6 倍的差距，後來又試了陣列語言 J，平均只要 70 個 token，比 Clojure 的 109 個還省。Google 的 AI 搜尋摘要也引用了這個結論，看起來好像很有說服力。

但作者自己也承認，另一個實驗有 bug，像是測試路徑根本不存在、agent 直接 symlink 到自己執行檔之類的問題。而且這些測試用的都是 Rosetta Code 那種極度簡單的題目，一個幾十個 token 就能解完的題目，真的能代表實際開發嗎？

## 我的觀點

2.6 倍這個數字確實很吸引眼球，但先把實驗設計攤開來看——那些題目多半是「印出答案」等級，根本碰不到真正寫程式的複雜度。在這種 trivial task 上，LLM 省下的 token 只是假象；一旦碰上需要多步驟邏輯、狀態管理、錯誤處理的任務，動態語言省下來的 type declaration 根本微不足道，反而可能因為缺乏約束而讓 model 產生更多不確定性。

我的判斷是：token 效率頂多算是一個「有趣的參考指標」，但絕對不該當作選擇程式語言的唯一理由。更別說那個實驗本身還有測試路徑錯亂的問題，連正確執行的路徑都不存在，這跟現實世界的 codebase 差距太大了。與其追求 token 數最小化，不如先確保 eval 題目有足夠的代表性，否則只是在玩數字遊戲。

## 延伸思考

如果未來真的因為 token 成本，讓陣列語言或極度精簡的語言重新受到重視，那會很有趣。但現實是，程式語言不只是寫給 AI 看的，更是寫給人看的。一個專案的維護成本、第三方套件生態、團隊熟悉度，這些都遠比 token 消耗重要。再說了，LLM 的 token 成本一直在下降，但除錯時間和系統複雜度反而可能上升，算總帳不見得划算。

另外我很好奇，如果改用「真實開源專案的 issue」當測試集，這些語言的 token 差距會不會縮小到幾乎看不出來？或者反過來，某些語言因為語法碎瑣，反而讓 LLM 更容易產生語法錯誤？這些都是值得後續實驗去驗證的。

> 📝 編輯說：: 這篇文章在程式開發圈被大量引用，筆者認為最有價值的觀點是提醒大家別迷信單一 token 效率指標，評估語言時還是要回到真實開發場景。

## 📰 3. AI Pulse：在 macOS Dock 旁顯示 AI 代理狀態的假 LED 燈條

🔗 [原文連結](https://github.com/leog/ai-pulse)


## 原文摘要

Hacker News 上有人丟出一個叫做 Show HN: AI Pulse 的專案，簡單說就是在 macOS Dock 旁邊加一條「假的」LED 燈條，用來顯示 AI 代理（Agent）目前的工作狀態。這條燈條不是真實硬體，而是用軟體畫出來的，看起來就像一條會發光的小燈條，會依照 AI 代理的狀況改變顏色或閃爍方式——閒置、忙碌、出錯、完成，一眼就能看出來。

原始文章沒有太多技術細節，重點就是這個概念：把 AI 代理的狀態變成一個環境提示，而不是要你一直打開終端機或網頁去查。作者把這個想法做成 macOS 上的小工具，讓使用者可以更直覺地掌握代理的動態。

## 我的觀點

你有沒有這種經驗？丟一個任務給 AI 代理，像是叫它跑測試、整理文件，然後你就切去別的視窗做事，過了五分鐘回來才發現它早就跑完了，或是卡在奇怪的迴圈裡等不到回應。這種「不知道現在到底在幹嘛」的焦慮感，真的很煩。

AI Pulse 就是衝著這個痛點來的。它用一條假 LED 燈條，把 AI 的狀態直接放在 Dock 旁邊，等於在桌面上掛了一個迷你狀態指示器。我覺得這個點子很聰明，而且有種復古的浪漫——就像老式主機板上的診斷燈，或是以前手機上的 LED 通知燈，明明只有幾個顏色，卻能用最不干擾的方式傳遞資訊。

更棒的是，它是「假」的燈條。不需要接 USB、不用焊電路板，也不怕燒掉，純粹用軟體模擬，想改顏色、改位置都容易。這很符合工程師的思維：能用程式解決的事，就不必硬體化。而且 macOS Dock 本來就是每天都會看到的東西，把狀態疊在這裡，既直覺又不佔
